GIS Migration: ESRI to Open-Source Stack

A comprehensive guide for migrating spatial data science workflows to Meta's internal infrastructure using open-source technologies.

📋 Author: Infra Intel Team 📅 Updated: January 2026 📌 Status: Draft

1 Executive Summary

▼

Objective

This document outlines the standard operating procedures for migrating Data Center Real Estate GIS workflows from ESRI (ArcGIS Online/ArcGIS Pro) to Meta's internal geospatial infrastructure. The goal is to leverage Meta's world-class enterprise-scale data architecture to deliver faster, more scalable, and more cost-effective spatial analytics and visualization capabilities.

Why Migrate? ESRI Limitations

While ESRI's ArcGIS platform has served as our primary GIS tooling, several limitations are driving the need for migration:

  • Scalability Constraints: ESRI's hosted feature services struggle with large datasets (millions of features), leading to slow query times and rendering issues
  • Cost Structure: Per-seat licensing and credit-based consumption models create unpredictable costs that scale poorly with organizational growth
  • Data Silos: Data stored in ESRI's ecosystem is isolated from Meta's broader data infrastructure, requiring manual ETL processes and duplicating storage
  • Limited Integration: Connecting ESRI services to internal data sources, authentication systems, and analytics pipelines requires significant custom development
  • Vendor Lock-in: Proprietary formats (File Geodatabases, Enterprise Geodatabases) and ESRI-specific APIs create dependencies that limit flexibility
  • Performance at Scale: Complex spatial queries and real-time analytics are constrained by ESRI's architecture, particularly for global datasets
  • Access Management: ESRI's sharing and permissions model doesn't align well with Meta's group-based access control patterns

Benefits of Meta's Enterprise Architecture

Meta's internal geospatial infrastructure offers significant advantages that address these limitations:

  • Petabyte-Scale Storage: Hive and Manifold provide virtually unlimited storage capacity with built-in redundancy and global replication
  • High-Performance Queries: Presto/Spark integration enables sub-second queries across billions of spatial features using distributed computing
  • Unified Data Platform: Direct integration with existing data warehouse tables eliminates ETL overhead and ensures single source of truth
  • Native H3 Support: Built-in H3 hexagonal indexing provides consistent spatial aggregation, fast point-in-polygon operations, and efficient tile generation
  • Enterprise Authentication: Seamless integration with Meta's identity management, enabling granular access control via existing groups and permissions
  • Cost Efficiency: No per-seat licensing—leverage existing infrastructure investments with marginal cost for additional users
  • Scheduled Pipelines: Chronos integration enables reliable, scheduled data refreshes with monitoring, alerting, and automatic retry logic
  • Customizable Frontends: Entrypoints and FBMap provide flexible UI frameworks that can be tailored to specific workflow requirements
  • Version Control & Reproducibility: All code, configurations, and pipeline definitions live in source control with full audit trails

Migration Approach

We will pursue a phased migration strategy starting with read-only visualization use cases before tackling editing and complex spatial analysis. This de-risks the transition and allows stakeholders to maintain productivity during the migration period.

Recommended Strategy: Choose one project (e.g., Parcel Query or Site Scout) to work out kinks and establish patterns, then apply lessons learned to subsequent projects.

The following projects have been identified for migration. Each project description includes its core functionality, data ingredients, and technical requirements.

1. Site Scout

Functionality: Interactive map-based tool for identifying and evaluating potential data center sites. Enables real estate analysts to explore geographic areas, filter by site criteria, and shortlist candidate locations.

Key Features:
  • Geographic search and filtering by region, country, or custom boundary
  • Multi-criteria scoring based on power availability, fiber connectivity, land cost, and regulatory environment
  • Side-by-side site comparison views
  • Export shortlisted sites for further analysis

Data Ingredients:

  • Global administrative boundaries (countries, states, municipalities)
  • Power grid infrastructure layers (substations, transmission lines, capacity data)
  • Fiber network routes and points of presence
  • Land parcel data with ownership and zoning attributes
  • Environmental constraint layers (flood zones, protected areas)

Requirements:

  • Fast tile rendering for global-scale exploration
  • Dynamic attribute filtering without full page reload
  • User-defined scoring weights with real-time recalculation
  • Integration with site evaluation workflows downstream

Key Features:

  • Team sharing with role-based permissions
  • Commenting and discussion threads anchored to map locations

Requirements:

4. H3 Layer Creation

Functionality: Utility tooling for generating H3 hexagonal grid layers from source data. Enables consistent spatial aggregation, privacy-preserving data publication, and optimized tile generation.

Key Features:
  • Convert point data to H3 cell aggregations
  • Generate H3 grids at specified resolutions
  • Aggregate polygon data to H3 cells (area-weighted)
  • H3-indexed data export for downstream tools

Data Ingredients:

  • Source point, line, or polygon datasets
  • Aggregation configuration (resolution, statistics to compute)
  • H3 resolution hierarchy definitions

Requirements:

  • Efficient H3 indexing at scale (Presto UDFs or Spark)
  • Support for multiple H3 resolutions (typically 4-9 for visualization)
  • Batch processing pipeline integration
  • Quality validation (no gaps, correct aggregation)

5. L-SIM (Land Simulation)

Functionality: Scenario modeling tool for simulating land use, development potential, and site configuration options. Supports "what-if" analysis for site planning and capacity estimation.

Key Features:
  • Buildable area calculation based on constraints
  • Facility footprint placement simulation
  • Capacity estimation based on land configuration
  • Constraint layer overlay (setbacks, easements, slopes)
  • Multiple scenario comparison

Data Ingredients:

  • Parcel boundaries and site polygons
  • Constraint layers (wetlands, setbacks, slopes, easements)
  • Building footprint templates and specifications
  • Zoning and development regulations

Requirements:

  • Geometric operations (buffer, difference, union)
  • Real-time recalculation as parameters change
  • 3D visualization (optional, for advanced scenarios)
  • Scenario save/load and comparison reporting

We recommend selecting one project to pilot before migrating the others. Good candidates for the pilot:

Working out kinks on the pilot will establish patterns, documentation, and reusable components that accelerate subsequent migrations.

A. Hive Tables (Primary for Large Data)

Best for: Structured spatial data with 100M+ records

-- Example Hive table schema for spatial data
CREATE TABLE your_namespace.spatial_data (
    id STRING,
    name STRING,
    status STRING,
    capacity_mw DOUBLE,
    geometry_wkt STRING,  -- WKT format: 'POINT(-122.4194 37.7749)'
    h3_index STRING,      -- Optional: H3 hex index for spatial queries
    created_date TIMESTAMP
)
PARTITIONED BY (region STRING)
STORED AS ORC;

4 Tile Serving & APIs

Super Map Maker (SMM) - Primary Tile Server

Generates vector tiles (MVT format) from any Hive table with WKT geometry.

phps VectorTileMaker <hive_table> \
  -b <build_name> \
  -w <wkt_column> \
  -g <geo_id_column> \
  -n <label_column> \
  -c "data,12,16,full" \
  --default-heatmap
Parameter Description
-bBuild name (unique identifier)
-wColumn containing WKT geometry
-gUnique ID column for each feature
-nLabel column for display
-cTile config (layer_name, min_zoom, max_zoom, detail_level)
⏱️ Build Time

A full global tileset typically takes 3-7 hours to generate.

5 Vector Tile Interactivity

🎯 Key Point

Vector tiles are fully interactive — they are NOT like ESRI Map Image Layers. All geometry and attributes are embedded in the tile, enabling click-to-identify, filtering, and dynamic styling without server round-trips.

Vector Tiles vs. Raster/Image Tiles

Capability ESRI Map Image Layer Vector Tiles (SMM)
Format Raster (PNG/JPEG) Vector (MVT - geometry + attributes)
Click to identify ❌ Requires server roundtrip ✅ Instant - data is in the tile
Client-side filtering ❌ No ✅ Yes - filter by any attribute
Dynamic styling ❌ No ✅ Yes - change colors on the fly
Hover effects ❌ No ✅ Yes
Attribute access ❌ Needs feature service ✅ Embedded in tile

Interactive Capabilities

1. Click to Identify Feature

map.on('click', 'your-layer', (e) => {
  const properties = e.features[0].properties;
  console.log(properties.name, properties.status, properties.capacity_mw);
  // Show popup, open detail panel, etc.
});

2. Client-Side Filtering (Instant, No Server Call)

map.setFilter('your-layer', [
  'all',
  ['==', ['get', 'status'], 'DELAYED'],
  ['>=', ['get', 'capacity_mw'], 500]
]);

3. Dynamic Styling Based on Attributes

map.setPaintProperty('your-layer', 'circle-color', [
  'match', ['get', 'status'],
  'BLOCKED', '#ef4444',
  'DELAYED', '#f59e0b',
  'WITHDRAWN', '#6b7280',
  '#3b82f6'  // default
]);

4. Hover Highlighting

map.on('mousemove', 'your-layer', (e) => {
  map.setFeatureState(
    { source: 'your-source', id: e.features[0].id },
    { hover: true }
  );
});

Limitations vs. Feature Services

Feature Vector Tiles ESRI Feature Service
Complex server-side queries ❌ No SQL on server ✅ Full SQL/spatial queries
Edit features ❌ Read-only ✅ CRUD operations
Real-time updates ❌ Requires tile rebuild ✅ Instant
Attribute simplification ⚠️ May reduce at low zooms ✅ Full attributes always
💡 Best Practice for Complex Queries

For complex server-side queries on large datasets (150M+ records), use a hybrid approach: Vector tiles for visualization + Laser/API backend for complex queries. The API returns matching IDs, and the frontend filters the tiles to show only those features.

Example: Convert Shapefile to Hive-ready format

import geopandas as gpd
import h3

# Read shapefile from Manifold
gdf = gpd.read_file('/mnt/manifold/your-bucket/data.shp')

# Convert geometry to WKT for Hive
gdf['geometry_wkt'] = gdf.geometry.apply(lambda g: g.wkt)

# Add H3 index for spatial queries
gdf['h3_index'] = gdf.geometry.centroid.apply(
    lambda p: h3.geo_to_h3(p.y, p.x, resolution=7)
)

# Export to Parquet for Hive upload
gdf.drop(columns=['geometry']).to_parquet('output.parquet')

Dataswarm Pipelines (Production ETL)

# ~/dataswarm/tasks/your_team/spatial_etl.py
from dataswarm.operators import GlobalDefaults
from dataswarm.operators.schemaoperator import PrestoInsertOperatorWithSchema

GlobalDefaults.set(
    schedule="0 9 * * *",  # Daily at 9 AM
    user="your_username",
    oncall="your_oncall",
)

# Step 1: Load data from Manifold to Hive
load_spatial_data = PrestoInsertOperatorWithSchema(
    name="load_spatial_data",
    table="your_namespace.spatial_data",
    query="""
        SELECT id, name, ST_AsText(geometry) as geometry_wkt, h3_index
        FROM manifold_source_table
    """,
)

# Step 2: Trigger Super Map Maker tile build
trigger_tile_build = BashOperator(
    name="build_vector_tiles",
    command="phps VectorTileMaker your_namespace.spatial_data -b your_build ...",
    dep_list=[load_spatial_data],
)

9 Migration Steps

💡 Migration Strategy

We recommend a phased approach starting with read-only visualization use cases. Select one project as a pilot to work out kinks, then apply lessons learned to subsequent migrations. Good pilot candidates: Parcel Query, Site Scout, or H3 Layer Creation.

Phase 1: Assessment (Week 1-2)

1.1 Inventory Spatial Datasets

  • Catalog all ESRI datasets (feature classes, tables, rasters)
  • Document sizes, record counts, geometry types
  • Identify update frequencies (real-time, daily, weekly, static)
  • Map data lineage and source systems
📋 Output: Data Dictionary spreadsheet with columns: Dataset Name, Type, Size, Record Count, Geometry Type, Update Frequency, Source, Owner, Notes

1.2 Identify ESRI-Specific Dependencies

  • Document usage of ESRI-specific features (geoprocessing tools, domains, subtypes, relationship classes)
  • Identify access management patterns (sharing levels, groups, named users)
  • Catalog custom widgets and web app configurations
  • Note any ESRI licensing dependencies (extensions, credits)
📋 Output: SOP page documenting dependencies and proposed mitigations for access management, group sharing, etc.

1.3 Inventory Spatial Pipelines

  • Document all scheduled tasks (Windows Task Scheduler, ArcGIS Notebook jobs)
  • Identify spatial calculations and geoprocessing workflows
  • Map trigger conditions and dependencies between tasks
  • Note failure handling and notification patterns
📋 Output: Pipeline and Task Dictionary spreadsheet with columns: Task Name, Schedule, Input Data, Output Data, Tools/Scripts Used, Dependencies, Notification Config

1.4 Identify Key Widgets & Functionalities

  • Catalog widgets used in existing web apps (Search, Filter, Query, Charts, etc.)
  • Document custom widgets and their functionality
  • Identify critical user workflows and interactions
  • Prioritize based on usage frequency and business value
📋 Output: Widget/Functionality inventory with priority rankings and Meta equivalent mappings

1.5 Develop Mitigations & Alternatives

  • Map each ESRI dependency to Meta equivalent or workaround
  • Identify gaps requiring custom development
  • Estimate effort for each mitigation
  • Document risks and contingencies

1.6 Create POCs for Each Project

  • Build minimal proof-of-concept for each in-scope project
  • Validate data migration path works
  • Test core functionality in new stack
  • Document lessons learned and blockers
🎯 Phase 1 Milestone: Complete inventory lists and POC status for all projects. Go/no-go decision for Phase 2.
Phase 2: Data Migration (Week 3-6)

2.1 Upload Raw Files to Manifold

  • Export ESRI data to portable formats (Shapefile, GeoJSON, FGDB)
  • Create Manifold bucket structure (organized by project/dataset)
  • Upload source files with metadata
  • Verify upload integrity (checksums, record counts)

2.2 Convert to WKT + H3 Format

  • Create Bento notebook templates for conversion
  • Reproject to WGS84 (EPSG:4326) as needed
  • Convert geometry to WKT strings
  • Generate H3 indexes at appropriate resolutions (typically 6-9)
  • Handle geometry validation and repair

2.3 Load to Hive Tables

  • Define Hive table schemas with proper data types
  • Load Parquet files to Hive tables
  • Validate record counts and data integrity
  • Set up partitioning strategy (by H3 prefix, date, region)

2.4 Test Upload & Retrieval

  • Query data via Presto to verify accessibility
  • Test spatial queries using H3 functions

Migration Script Template

#!/usr/bin/env python3
"""migrate_esri_to_hive.py - Converts ESRI geodatabase to Hive-compatible format"""

import geopandas as gpd
import h3

def migrate_dataset(input_path: str, output_path: str, h3_resolution: int = 7):
    # Read ESRI data
    gdf = gpd.read_file(input_path)

    # Reproject to WGS84 if needed
    if gdf.crs != 'EPSG:4326':
        gdf = gdf.to_crs('EPSG:4326')

    # Convert geometry to WKT
    gdf['geometry_wkt'] = gdf.geometry.apply(lambda g: g.wkt if g else None)

    # Add H3 index for spatial queries
    def get_h3(geom):
        if geom is None:
            return None
        centroid = geom.centroid
        return h3.geo_to_h3(centroid.y, centroid.x, h3_resolution)

    gdf['h3_index'] = gdf.geometry.apply(get_h3)

    # Write to Parquet for Hive
    df = gdf.drop(columns=['geometry'])
    df.to_parquet(output_path, index=False)
    print(f"Migrated {len(df)} records to {output_path}")

if __name__ == "__main__":
    migrate_dataset("/mnt/manifold/bucket/source.gdb", "/mnt/manifold/bucket/output.parquet")

CREATE TABLE your_namespace.large_spatial_data AS
SELECT *, h3_geo_to_h3(lat, lon, 7) as h3_index
FROM source_table;

SELECT * FROM large_spatial_data
WHERE h3_index IN (
    h3_k_ring('87283082bffffff', 2)  -- 2-ring around target cell
);
